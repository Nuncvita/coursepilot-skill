# Architecture Explanation For Judges

## 为什么 CoursePilot 不只是一个 Prompt

如果一个作品只有单条 Prompt，它往往很难回答三个问题：

1. 它稳定的能力边界是什么
2. 它如何适配不同平台
3. 它后续如何继续优化和迁移

CoursePilot 引入双层架构，就是为了把"能力本体"和"平台接入方式"拆开，让作品更像一个可持续演进的 Skill，而不是一次性指令集合。

## 反证：为什么不用单层架构

| 问题 | 单层架构 | 双层架构 |
|---|---|---|
| 换平台需要改多少 | 全部重写 | 只改 platforms/ |
| 能力规则在哪 | 散在 Prompt 各处，难以定位 | 集中在 core/，一处定义多处复用 |
| 新平台适配成本 | 高（从零开始） | 低（引用 core 层 + 写适配入口） |
| 多平台口径一致性 | 难保证（各平台独立维护） | 有保证（共享同一能力层） |
| 后续产品化 | 需要重新拆分 | 已经拆好，直接扩展 |

## 架构总览

```
┌──────────────────────────────────────────────────┐
│  platforms/  — 平台适配层（只做适配，不定义能力）  │
│                                                  │
│  ┌────────────┐ ┌────────────┐ ┌────────────┐   │
│  │ chatgpt    │ │ codebuddy  │ │ clawpro    │   │
│  │ _skill     │ │ _cli       │ │            │   │
│  │            │ │            │ │            │   │
│  │ SKILL.md   │ │ 使用计划   │ │ Prompt     │   │
│  │ (轻量入口) │ │ 检查清单   │ │ 配置计划   │   │
│  │            │ │ 优化记录   │ │ 演示步骤   │   │
│  └─────┬──────┘ └─────┬──────┘ └─────┬──────┘   │
│        │              │              │           │
│        └──────────────┼──────────────┘           │
│                       │ 引用                      │
├───────────────────────┼──────────────────────────┤
│  core/  — 平台无关能力层（只定义能力，不做适配）  │
│                       │                           │
│  capability_spec.md   ← 输入/输出/关键能力/非目标 │
│  workflow_core.md     ← 15 步工作流 + 数据流      │
│  output_templates.md  ← 10 个输出模板              │
│  user_learning_style  ← 默认 Nuncvita 风格 + 多风格│
│  learning_style_sel   ← 风格选择/预览/混合风格     │
│  evaluation_rules.md  ← 10 条质量检查             │
│  safety_and_privacy   ← 安全/隐私/版权/诚信       │
└──────────────────────────────────────────────────┘
```

## 能力层沉淀了什么

`core/` 沉淀的是平台无关的稳定能力，包括：

| 能力 | 文件 | 核心内容 |
|---|---|---|
| 能力定义 | capability_spec.md | 输入/输出类型、8 项核心能力（按优先级排序）、降级策略、非目标 |
| 工作流 | workflow_core.md | 15 步流程、步骤间数据流、异常与降级处理 |
| 输出模板 | output_templates.md | 8 个模板、必填字段、质量要求、输出组合策略 |
| 学习风格 | user_learning_style.md | 默认 Nuncvita 风格 + 7 种可选风格 |
| 风格选择器 | learning_style_selector.md | 粗分类选择、风格预览、混合风格、5 问题确认 |
| 质量检查 | evaluation_rules.md | 10 条自检规则 |
| 安全边界 | safety_and_privacy.md | 版权、隐私、来源、承诺、诚信 5 层边界 |

这些内容不依赖具体平台，因此可以长期复用。

## 平台层适配了什么

`platforms/` 只负责把能力层接到不同平台，不定义任何能力规则：

| 平台 | 职责 | 入口文件 |
|---|---|---|
| chatgpt_skill | 保留标准 SKILL.md 入口，引用 core 层 | SKILL.md |
| codebuddy_cli | 为官方工具优化提供执行计划、Prompt 和记录 | codebuddy_cli_usage_plan.md |
| clawpro | 为 Skill/Agent 配置、运行和演示提供文件 | clawpro_prompt.md |

关键原则：**平台层不重复定义能力规则，只做适配和引用。** 这样才能保证多平台口径一致。

## CodeBuddy CLI 如何参与工程化优化

CodeBuddy CLI 的角色不是替代 CoursePilot 的能力，而是：

- 检查双层架构是否合理（core 是否平台无关，platforms 是否只做适配）
- 优化 README、能力规范和平台 Prompt
- 检查样例是否更适合评委阅读
- 形成官方工具参与的日志与截图证据

这使作品不仅有内容，还具备工程化打磨过程。

## ClawPro 如何参与平台运行展示

ClawPro 的角色是把 CoursePilot 配成可运行的 Skill / Agent，并完成：

- Prompt 粘贴（使用 clawpro_prompt.md）
- 输入字段配置（使用 clawpro_input_output_schema.md）
- DSP 样例测试
- 输出截图
- 演示视频录制

这为比赛展示提供了平台运行态证据，而不只是本地文档。

## 默认风格 + 可配置风格系统

CoursePilot 不是强迫所有用户使用同一种讲义风格，而是提供了灵活的风格配置系统：

1. **默认风格来自真实成功案例** — Nuncvita / 默认高效复习型源自一次真实的 DSP 课程期末复习实践，经过验证的学习方案
2. **7 种粗分类风格可选** — 涵盖零基础补课、考试速通、公式推导、例题训练、严谨教材、冲高分拓展等不同需求
3. **风格预览机制** — 用户上传资料后，可用 2-3 种风格预览同一知识点（每种 5-8 行），看到差异后再选择
4. **混合风格支持** — 用户可以为主讲义、公式部分、练习部分、考前冲刺分别指定不同风格
5. **5 题快速确认** — 如果用户未提供偏好，最多 5 个选择题即可完成风格配置，用户可直接选"默认"跳过
6. **随时可切换** — 用户在任何时候都可以说"换成 XX 风格"或"这部分用 XX 风格重讲"

这一点增强了 CoursePilot 的产品化和可迁移性：不同学习基础、不同目标分数、不同时间紧迫度的学习者，都能获得适合自己的输出格式，而不是被迫接受固定风格。

## 双层架构为什么利于复用、迁移和产品化

1. **能力层稳定后，可复用于多个平台** — 同一套能力定义，接入 ChatGPT、ClawPro 或未来新平台时无需重写
2. **平台迁移时，只需重写适配层** — 从 ClawPro 迁到另一个 Agent 平台，只改 platforms/ 目录
3. **多平台口径一致** — 所有平台引用同一套 core 规则，不会出现自相矛盾
4. **有利于后续产品化** — 作品可以讲成"可复用的教育 Skill 架构"，而不是"单课程临时方案"

因此，这一结构既服务比赛展示，也服务后续产品化路径。
